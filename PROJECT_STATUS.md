## What OpsGenie is

A WhatsApp-first daily financial operating assistant for B2B distributors. It ingests existing business records (Tally / Vyapar / Excel exports), maintains a **deterministic** ledger of invoices / payments / dealers / suppliers, and delivers daily cash-position briefings, on-demand reports, and guided write actions (record a payment, create an order/invoice, update GST/stock) entirely over WhatsApp — with an LLM layer for narration and free-form Q&A, but **never** for owning business state or doing money math.

Built solo, targeting real distributor pilots (not a demo).

## Timeline: what's been built, in order

### Phase 0 — Project foundation
Repo scaffolding, FastAPI app factory, config / logging / exception-handling core, health check.

### Phase 1 — Database schema
All ORM models + first Alembic migration. (SPEC named 13 tables; the schema has since grown to 17 as write features landed.)

### Phase 2 — Admin CRUD
`company` / `dealer` / `supplier` create/read endpoints (founder-facing, `X-API-Key` gated).

### Phase 3 — Import pipeline
Pluggable importer architecture (Tally / Vyapar / Canonical CSV/Excel), idempotent invoice + payment import with **FIFO payment allocation**. First real-pilot-data validation here.

### Phase 4 — Invoice/payment read APIs
Filterable list endpoints with computed `amount_paid` / `amount_outstanding`.

### Phase 5A — Business engine (pure Python, no LLM)
`BusinessSnapshotService`, `DealerOutstandingCalculator`, `RecommendationEngine`, `GET /admin/companies/{id}/cashflow`. Split from 5B so the deterministic engine shipped and was validated before any LLM code existed.

### Phase 5B — LLM briefing/narration layer
`BriefingService` narrates the 5A snapshot. Built as a **pluggable multi-provider failover chain** (`app/services/llm/`): Claude / Gemini / Groq / OpenRouter / GitHub Models / Cohere, selected & chained via `.env` (`LLM_PROVIDER` + `LLM_FALLBACKS`). Verified in production: a real OpenRouter 429 failed over to Gemini with identical figures. Money is never invented by the LLM — every figure comes from the deterministic snapshot.

### Pre-Phase-6 production hardening
Money math corrected (outstanding, not gross, in 7-day windows), business-timezone boundaries (`Company.timezone`, IST), `uv.lock` committed, deploy migration step, upload size cap, health endpoint leak fix.

### Phase 6 — Auth + pagination
Single shared `ADMIN_API_KEY` (fails closed, generic 401), `Page[T]` pagination on all 5 list endpoints (limit capped at 200).

### Phase 7 — WhatsApp inbound webhook (V0.1 Step 11)
`GET`/`POST /webhooks/whatsapp` with its own two security mechanisms (verify-token handshake + `X-Hub-Signature-256` HMAC over raw body). Parses Meta payloads, matches sender to a `Company`, durably logs every message/status as a `BusinessEvent`.

### Phase 8 — Numbered query menu (V0.1 Step 12)
Generic `CommandRouter`, first-ever outbound sender (`whatsapp_client.py`), four canned reports (Cash / Collections / Suppliers / Dealer Risk) built strictly from snapshot fields. End-to-end traceability: inbound event → reply → Meta wamid → `NotificationLog` → status webhook. Idempotency against Meta redelivery.

### Phase 9 — Invoice due-date follow-up (V0.1 Step 13)
`InvoiceDueDateFollowUpService` — a full WhatsApp state machine ("Has payment been received? 1 Yes / 2 Partial / 3 Not yet") routing replies back through payment recording. One active follow-up per company at a time; deterministic-only date parsing.

### Phases 10–12 — Notifications + scheduler + stale-data banner (V0.1 Steps 14–16)
`NotificationEngine` (4 pure-rule alerts, internal dedup), `APScheduler` single-poll tick honoring each company's business-local hour, stale-data banner on briefings. **Completes all of V0.1.**

### Import: honor a paid/outstanding amount already in the source file (2026-07-20)
Same QA pass surfaced a second, more serious bug: the invoices importer (`app/services/importer/engine.py`, shared by Tally/Vyapar/Canonical and both the onboarding and founder-admin import routes) silently dropped a source file's "Paid Amount"/"Outstanding" columns — every imported invoice was hardcoded `status=InvoiceStatus.Pending` with no `Payment` row, regardless of what the file actually said. The onboarding reconciliation screen showed gross invoice totals (₹2,64,250 receivable / ₹5,38,100 payable) instead of real outstanding (₹1,11,250 / ₹2,96,100) — and because it's the same importer the founder admin route uses, any historical import of already-partially-paid invoices would overstate "amount owed" everywhere downstream (WhatsApp balance queries, snapshots, ledger reports), not just on one screen.
- New `OPTIONAL_MONEY_ALIASES` + `infer_optional_money_columns` (`engine.py`) resolve `paid_amount`/`outstanding_amount`/`payment_date` once, centrally, for every format — not Tally- or Vyapar-specific vocabulary, so it doesn't belong duplicated across `tally.py`/`vyapar.py`/`canonical.py`'s own alias maps. On top of the widened exact-match list, a narrow whole-token keyword fallback (`_infer_money_column`) catches a spelling that isn't in that list at all — direct user feedback ("column names won't always be the same, don't hardcode") balanced against this codebase's usual preference for deterministic column matching over guessing: the fallback never overrides an exact alias, is scoped only to these two optional fields (never a required column), and has an explicit guard so a header like "Payment Due Date" (tokenises to `{"payment","due","date"}`) is never mistaken for an amount column just because it contains "due".
- `_import_invoice_row` now derives the real `InvoiceStatus` (Paid/Partially_Paid/Pending) from the resolved paid amount and creates a matching `Payment` row (mirroring `payment_row.py`'s pattern) instead of hardcoding `Pending` — `party_outstanding.py`'s netting was already correct, it just had zero `Payment` rows to net against before this.
- 6 new regression tests in `test_import_engine.py` (paid-amount column, outstanding-amount column + derived-Paid status, an invalid paid>total row failing that row only, the untouched default with neither column present, the keyword fallback catching an untested spelling, the due-date guard not misfiring). Verified against the real QA files end-to-end (register → import → reconciliation summary): totals corrected to the real outstanding amounts.

### Whole-codebase bug audit + 8 fixes (2026-07-23)
A full "every bug and minor issue since the start" pass over ~32k LOC, run as four parallel domain audits (money/ledger core · WhatsApp conversation layer · scheduler/notifications/reports · API/security/persistence/migrations), with every CRITICAL/HIGH claim independently re-verified in source before being acted on. Roughly 60 findings; the 8 below were fixed this session, each with a regression test that was **explicitly checked to fail with the fix reverted** — one first-draft test turned out to be vacuous (see the FAQ item), which is why that verification step is now part of the routine rather than assumed.

Four root causes explained most of the findings, and are worth remembering as recurring shapes in this codebase: **(a)** commit boundaries not matching send boundaries (a real WhatsApp message goes out before the transaction that records it commits); **(b)** the four single-slot conversation pointers (`onboarding_state`, `active_workflow`, `active_pending_operation_id`, `pending_follow_up_invoice_id`) each being guarded against a *different subset* of the others; **(c)** `Cancelled`/`Draft` status filtering applied in `reports/`+`trend_analytics.py` but not `daily_snapshot.py`; **(d)** no CI, so none of it was caught mechanically.

1. **`delete_payment` silently voided money** (`app/api/admin/payments.py`) — deleted the row without recomputing `Invoice.status`, and the dashboard exposes it as a one-click button (`app/api/dashboard/payments.py`). Deleting the ₹50,000 payment on a `Paid` ₹50,000 invoice left status `Paid`, which `_OPEN_STATUSES` excludes — so `calculate_party_outstanding` reported **₹0** for money owed again, while `reports/ledger.py` (filters only Draft/Cancelled) still showed the full balance. Two reports the distributor can hold side by side, disagreeing by the full amount, with nothing to reconcile them. Fixed by reusing the guided-workflow path's own rule; `_recompute_invoice_status` → **`recompute_invoice_status`** (`writes/void.py`), promoted to public because three modules now depend on it (same promotion convention used earlier for `recently_messaged`).
2. **Notification re-send storm** (`app/services/notifications.py::run_notification_checks`) — all five rules shared one caller-side commit. Every rule sends real WhatsApp messages *before* writing its dedup marker, so any failure mid-pass rolled back markers for messages already delivered, and the 10-minute external cron re-sent them indefinitely. This is the shape of the July 2026 founder-flood incident. Now commits after each rule, matching `writes/broadcast.py`'s existing per-recipient contract; `_dispatch_for_company`'s docstring already stated this principle for the four top-level concerns, it just wasn't applied *within* the pass. The test verifies durability **from a separate session** — the failed session's own state can't answer "did this reach the database?", which is what the next tick actually sees.
3. **Partial writes committed while telling the user it failed** (9 call sites in `writes/pending_operation.py` + `workflows/stock_take_flow.py`) — no write path used a savepoint (only the three CSV importers did), and the webhook commits unconditionally at `whatsapp.py:1381`. `apply_stock_take` mutates each product and adds its audit event as it loops, then raises if a later product is gone: the earlier products stayed committed under a "stock take failed" reply, contradicting that function's own docstring. Every non-self-committing write service is now wrapped in `db.begin_nested()`, the same pattern the importers use. **`send_broadcast` is deliberately excluded** — it commits internally by design, and a savepoint around a self-committing function defeats both; its idempotency comes from `batch_id` (below) instead.
4. **A follow-up could hijack a live money confirmation** (`followup.py` + `notifications.py`) — root cause (b). `send_due_today_follow_up` claimed its slot checking *only* `pending_follow_up_invoice_id`; `check_supplier_payment_reminders`'s `can_start_confirm` checked the other two but not it. Since pending operations outrank follow-ups in the webhook's `elif` chain, a follow-up pushed on top of "Reply YES to confirm" made the founder's `1` (meaning "the dealer paid in full") land in `_YES_WORDS` and **execute the pending order**, silently dropping the payment they meant to record; `2` cancelled a write they never meant to cancel. Both guards now check all three pointers, and the follow-up's atomic claim includes them in its `WHERE` so the race is closed too, not just the read.
5. **A crashed broadcast re-blasted the whole dealer network** (`writes/broadcast.py`) — it is the only webhook-reachable service that commits mid-request (deliberately, so the audit trail survives), which breaks the webhook's "no committed reply event ⇒ resume and re-run" idempotency contract: a failed final commit meant Meta redelivered, the still-present `PendingOperation` re-executed, and every dealer got the marketing message twice. New **`NotificationLog.batch_id`** (nullable, indexed — migration `b7c1e9d43a52`) carries the confirming `PendingOperation.id`, which is stable across exactly that redelivery *because* the delete is what failed to commit. Recipients already logged for the batch are skipped, so a crash resumes instead of re-sending.
6. **The GST Sales/Purchase Registers were empty for the live pilot** (`reports/registers.py`) — `_register_rows` inner-joins `InvoiceItem`, and `InvoiceItem` is constructed in exactly **one** place in the whole codebase (`writes/orders.py`, the WhatsApp order flow). The CSV/Tally/Vyapar importers create the `Invoice` alone, so a distributor whose books arrived by Tally export got a header with nothing under it (`if rows:` suppresses even the TOTAL row) while their Day Book and invoice lists showed the same invoices correctly — wrong output that looked like missing data. Now unions a synthesized `_InvoiceLevelLine` per item-less invoice, built from that invoice's own `subtotal`/`gst_amount`, labelled `(invoice total — no line detail on file)` so it's never mistaken for real line detail, with the rate backed out and **rounded to whole percent** (real slabs are integers; rounded rupee totals otherwise yield noise like 17.98% that fragments the rate-wise summary). Both sources are re-sorted together so imported invoices interleave by date rather than bunching after the itemised ones.
7. **Public onboarding leaked a UUID that unlocked an unauthenticated write** (`app/api/onboarding.py`) — `POST /onboard` returned `company_id` on the `already_registered` branch. A WhatsApp number is public (printed on invoices, encoded in the wa.me link), so anyone could post a real distributor's number, get their UUID, and use it against `/onboard/{id}/import` — which writes dealers/suppliers/invoices into their books *and* echoes back their real receivable/payable totals. `_get_importable_company`'s own docstring says its state gate exists to stop "any leaked/guessed UUID"; the register endpoint was handing that UUID out. New **`app/services/onboarding_token.py`**: stateless HMAC over `company_id:expires_at`, same pattern as the export links, no migration. Three deliberate choices — the signed message is prefixed `onboarding:` so an export-link signature can never be replayed as an onboarding token; `ONBOARDING_TOKEN_SECRET` **falls back to `EXPORT_LINK_SECRET`** so this deploys with no new production env var while still failing closed if neither is set; and a bad token returns **404, not 401**, matching what these routes already return for an ineligible company so the status code can't distinguish "exists but you lack a token" from "no such company" — that distinction *is* the oracle.
8. **The activate gate was written inverted** (same file) — it rejected only `completed AND inactive`, so every *other* inactive state passed, meaning a company the founder had suspended mid-onboarding could be switched back on through the public route, re-enabling its WhatsApp agent and firing a billable Meta welcome template. Now gated on `not_started`, **but** restructured rather than tightened outright: a strict gate would have broken the route's existing idempotency contract (`test_activate_idempotent_second_call` — after activation `subscription_active` is True, so a `not_started`-only gate would 404 a legitimate double-click). An already-active company is now a no-op for a valid token-holder; the `not_started` requirement applies only to the not-yet-active case.

Also fixed: **two pre-existing test flakes** that were failing the suite independently of any of this — `test_company_export.py::_unique_phone()` generated a leading digit outside 6-9 about 60% of the time (invalid Indian mobile → onboarding rejects → `KeyError: 'company_id'`, the flake noted below under Trend analytics), and `test_public_export_endpoint_rejects_tampered_signature` flipped the signature's last character to a hardcoded `"0"`, so ~1 run in 16 it produced an *identical* valid signature and passed a tampered-link check it had never actually performed. `.env.example` gained `ONBOARDING_TOKEN_SECRET` and the previously-undocumented `DEFAULT_PHONE_REGION`.

**`FAQ` was missing from `app/models/__init__.py`** — a separate fix worth its own note. Runtime was unaffected (`app.main` pulls `FAQ` in transitively via the admin router), which is exactly what hid it, but `alembic/env.py` sets `target_metadata = Base.metadata` after importing *only* `app.models`, so `Base.metadata` held 16 of 17 tables and the next `alembic revision --autogenerate` would have emitted `op.drop_table("faqs")`, silently deleting every distributor's curated FAQ content. The guard test runs its check in a **subprocess** that imports only `app.models`: the first version passed with the bug deliberately reverted, because `conftest` imports `app.main` — it was reproducing the blind spot instead of the bug.

Full suite green (**1,002 tests**), ruff clean, migration graph still single-head. Findings deliberately **not** fixed this session are listed under "Known gaps / tech debt" below.

### Payment-reminder/follow-up busy messaging + failed-send dedup fix (2026-07-24)
Two bugs reported directly off the live product via real WhatsApp screenshots (a supplier payment reminder conversation, then a "help"/"menu" attempt that got no reply at all).
1. **"help"/"menu" mid a payment-reminder or dealer follow-up conversation was swallowed into a confusing restatement.** Both `app/services/workflows/payment_reminder_confirm.py::handle_reminder_confirm_workflow_message` and `app/services/followup.py::handle_follow_up_reply` already outrank the menu/instant-command tier in the webhook's priority ladder (a bare "1"/"2" mid-conversation must answer the conversation, not trigger a menu command) — but that meant typing "help" while either conversation was active fell through to the flow's own generic "didn't understand, reply 1/2" restatement, with nothing telling the founder *why* their "help" didn't do anything. New shared behavior (mirrored identically in both modules, each keeping its own local `_ORIENTATION_WORDS` constant per this codebase's existing small-constant-duplication precedent): `help`/`/help`/`menu`/`/menu`/`commands`/`what can you do` now get a new `workflow.busy_reply_first` reply ("Please reply to this first, then you can continue with your next message.") with the flow's actual current question re-rendered underneath — reusing the exact same question-rendering each flow already had for its own first-ask/invalid-choice paths, so the restated text can never drift from what was actually asked. Deliberately **not** a cancel — the conversation keeps waiting exactly where it was, unlike the existing `cancel`/`stop` escape hatch which clears it.
2. **A real WhatsApp send failure permanently and silently blocked any future reply to that message.** `app/api/webhooks/whatsapp.py::_send_reply_and_log` wrote the `whatsapp_reply_sent` dedup marker (what `_reply_already_sent` checks to decide whether a Meta redelivery should be skipped) unconditionally — even when the actual `send_text_message`/`send_interactive_list_message` call failed (`WhatsAppSendError`, caught and logged, never raised). So a transient WhatsApp Cloud API hiccup meant the founder's phone received nothing, the failure was correctly recorded as `NotificationLog.delivery_status="failed_to_send"`, but the message was *also* marked "already replied to" — permanently, since nothing ever re-triggers a retry once that marker exists. This is the same root-cause shape (commit/send-boundary mismatch) the 2026-07-23 audit already fixed in `notifications.py`'s five proactive rules, just never applied to the webhook's own reply-to-inbound-message path. Now the marker is only written when `send_result is not None` (a real success) — a failed send leaves no marker, so a genuine Meta redelivery of that exact message resumes and retries the send instead of going silent forever. Most likely explanation for the reported "/help produced literally nothing," though not reproduced as a deterministic logic bug in the dispatch code itself (which correctly routes "help" → the real help text every time it runs).

New i18n key `workflow.busy_reply_first` across all 5 locale catalogs (parity + placeholder tests green). 11 new tests: `tests/test_payment_reminder_confirm.py` (new file, 7 tests — no dedicated coverage existed for this module before; covers `start_reminder_confirm`, the existing invalid-choice/cancel paths, the new orientation-word behavior at all three steps, and a "still finishable after asking for help" proof), 3 new in `tests/test_followup_service.py` (orientation words at each of the three follow-up states), 1 new in `tests/test_webhooks_whatsapp.py` (`test_failed_send_does_not_block_a_later_retry` — a mocked send that fails once then succeeds, asserting the redelivery actually retries rather than being skipped, exactly one inbound event, exactly one `whatsapp_reply_sent` marker). Full suite green, `ruff check app/ tests/` clean.

### Edit / correction / data-management — complete (2026-07-19)
All four built as guided WhatsApp workflows reusing the existing architecture (`PendingOperation` confirm gate for money-affecting writes, write-immediately for attribute edits — matching `update_product`'s existing tier), with a generic `BusinessEvent`-based audit trail (`{field, old, new, reason}`, `reason` optional) on every one. See `app/services/workflows/void_flow.py`, `edit_flow.py`, `party_flow.py`'s edit-dealer/edit-supplier additions, `stock_take_flow.py`, and their `app/services/writes/*` counterparts.
- [x] **Undo / void** a payment or order — targets only the single most-recently WhatsApp-recorded one (`"undo payment"`/`"undo order"`); voiding an order with a payment already against it is refused (void the payment first). Soft-cancels the invoice (`InvoiceStatus.Cancelled` — the enum value existed but nothing ever set it before this) rather than hard-deleting, restores stock.
- [x] **Edit an invoice/payment** (amount, date, party) with a full audit trail — **deliberately scoped to safe cases only** after a design review cut a more "clever" automated FIFO-reallocation version (release money from one invoice, re-spill it across a party's other open invoices) for being hard to explain and the highest-risk surface in the whole feature. An invoice with *any* payment recorded is refused outright, regardless of field — points to void-and-recreate instead. A payment's amount edit is bounds-checked only against its own invoice's total; it never moves money to a different invoice. Cross-party payment reassignment is out of scope this iteration, to reconsider only if pilot users actually ask for it.
- [x] **Edit party details over WhatsApp** — phone, credit limit, payment terms, GSTIN, for both dealers and suppliers (`Supplier` gained a `gst_number` column — it had none before, only `Dealer` did). New `validate_gstin()` (format + mod-36 checksum) in `app/services/gst.py`, also closing out part of the "GSTIN format validation" item below.
- [x] **Stock-take / bulk stock adjustment** flow — loops over multiple products in one session, accepting either an absolute recount (`40`) or a signed delta (`+15`/`-3`); negative resulting stock is flagged, not blocked (same convention `create_order` already uses).
- [ ] **Deferred: edit an already-paid invoice/payment beyond the safe cases** — today, editing an invoice with any payment recorded is refused outright (points to void-and-recreate), and a payment's amount edit can never move money to a different invoice. An earlier design pass sketched what real support would need: release the excess/freed amount from the edited invoice or payment, then re-run `allocate_payment_fifo` (`app/services/importer/payment_row.py`) against the party's other open invoices to re-place it — reusing the exact function CSV import and `record_payment` already call, no new allocation engine needed. Cross-party payment reassignment (moving a payment to a different dealer/supplier entirely) was dropped from scope even further back and would need the same reallocation primitive plus a decision on where a payment "belongs" when it was originally split across invoices.

## Working principles (how this project is built)
- **Phase discipline** — deterministic business engine solid and real-data-validated before any AI; money math never touches the LLM.
- **Writes are guided workflows**, not AI tool-calls — a confirm gate (`PendingOperation`) re-derives the write fresh at confirm time.
- **No blended financial metrics** — accrual (margin) and cash-basis (collections/payments) are always reported separately.
- **Never commit generated output** (Excel/PDF/static site are built at request/deploy time).
- **Before closing work**: full pytest green + `ruff check` clean + a structured multi-angle review.
